Provider names take the form `<org>/<name>`, for example `pragmatiks/postgres`.

## Initialize

Create a new provider project from the template:

```bash
pragma providers init mycompany
```

With options:

```bash
pragma providers init mycompany --directory ./providers/mycompany --defaults
```

`--description`, `--author`, and `--email` fill in the project metadata; `--defaults` skips the prompts.

## Update

Merge template changes into an existing project, keeping your customizations:

```bash
pragma providers update
pragma providers update ./my-provider
```

## Publish

Publish a new version of a provider under your organization:

```bash
pragma providers publish [PROJECT_DIRECTORY | --wheel <path>] [--changelog <file>] [-o json|yaml]
```

```bash
pragma providers publish
pragma providers publish ./my-provider --changelog NOTES.md
pragma providers publish --wheel dist/my_provider-1.0.0-py3-none-any.whl
```

Without `--wheel`, publish builds the wheel with `uv build` into `<project-dir>/dist` (the current directory by default), so a uv workspace member's wheel lands in its own `dist/`. A project directory and `--wheel` cannot be combined. Passing both, or a project directory that does not exist or has no `pyproject.toml`, exits 2.

The wheel alone identifies the version: its `pragma.provider` entry point names the provider and its metadata carries the version. Published versions are immutable.

Publish renames a copy of the wheel to your organization's distribution name, `<organization>-<provider>`; the file you built or passed with `--wheel` is left unchanged. It then declares the version, uploads the renamed copy straight to the signed upload address the declaration returns, and follows the version until it is `published` or `failed`:

```text
Renamed to myorg_my_provider-1.0.0-py3-none-any.whl
Publishing myorg/my-provider 1.0.0
Uploaded 12.3 KB
Status: wheel received
Status: admitting
Published myorg/my-provider 1.0.0 — Python …, SDK …, 2 resource types
```

Progress goes to stderr; only the `Published` line goes to stdout. With `-o json` or `-o yaml`, stdout carries one document, `{"operation_id": …, "version": …}`, once the watch ends. See [Publishing Providers](/building-providers/publishing) for each step and the version statuses.

| Exit code | When |
|-----------|------|
| `0` | The version is `published` |
| `1` | The version failed or was replaced by another publish, the renamed copy could not be written, the declaration was refused, or the upload was refused or its address expired |
| `2` | Invalid usage, a missing project directory, a failed build, or a wheel that cannot be read |
| `3` | The wheel was uploaded or already received, then the watch ended with the version unsettled or could not read it; run the printed [`pragma providers wait`](#wait) command to keep waiting |

## Wait

Keep waiting for a version a publish declared, after publish exits 3:

```bash
pragma providers wait <name> <version> --operation <operation-id> [-o json|yaml]
```

```bash
pragma providers wait myorg/my-provider 1.0.0 --operation 3f2c9a
```

Publish prints this command, with its operation id, when it exits 3. Wait follows the version the same way publish does and reports a version that already settled at once; nothing is declared or uploaded again. With `-o json` or `-o yaml`, stdout carries the same document as publish.

| Exit code | When |
|-----------|------|
| `0` | The version is `published` |
| `1` | The version failed, or another publish of the version replaced the one `--operation` names |
| `3` | The watch ended with the version still unsettled or could not read it; run the printed command to keep waiting |
| `4` | The version does not exist |

## Versions

List a provider's versions with their status:

```bash
pragma providers versions myorg/my-provider
```

The Status column shows `waiting for the wheel`, `wheel received`, `waiting for the provider host`, `admitting`, `publishing to the registry`, `published` or `failed`, and the Message column shows a failed version's failure message.

## Install

Install a provider in your organization:

```bash
pragma providers install pragmatiks/qdrant
pragma providers install pragmatiks/postgres --version 1.2.0
pragma providers install pragmatiks/qdrant --config SOME_KEY=some_value
pragma providers install pragmatiks/qdrant --config-file config.yaml
```

Without `--version`, the latest version is installed. `--yes` skips the confirmation prompt.

The command prints the version the installation targets and the command to follow it:

```text
Install queued: pragmatiks/qdrant v1.4.0
Follow it with: pragma providers history pragmatiks/qdrant
```

The installation then continues on its own: it is queued, starts, and ends running or failed. See [Installation lifecycle](#installation-lifecycle).

## List

List providers in the catalog, or only the installed ones:

```bash
pragma providers list
pragma providers list --installed
pragma providers list --query postgres
pragma providers list --scope public --tags ml,vector
```

`--installed` shows one row per installed provider:

| Column | Shows |
|--------|-------|
| Provider | The provider name |
| State | `Queued`, `Starting`, `Draining`, `Translating`, `Switching`, `Running`, `Failed` or `Uninstalling` |
| Version | The version the installation serves; a dash until it first runs |
| Operation | While an operation runs, the operation (`install`, `upgrade`, `downgrade`, `restart` for a host start, `uninstall`) and the version it targets; a dash once it settled |
| Message | Why the installation failed, when it failed |

With `-o json` or `-o yaml`, each record carries `installed_version`, `lifecycle_state` (`pending`, `processing`, `draining`, `translating`, `swapping`, `ready`, `failed` or `deleting`), `operation_type`, `operation_version`, `operation_running` and `failure_message`.

## Info

Show a provider's metadata, version history, and installation status:

```bash
pragma providers info pragmatiks/qdrant
```

## History

Show the history of an installed provider, newest first:

```bash
pragma providers history pragmatiks/postgres
pragma providers history pragmatiks/postgres -o json
```

| Column | Shows |
|--------|-------|
| Time | When the transition happened |
| Transition | The states it moved between, such as `Queued -> Starting`; `Uninstalled` once the provider is uninstalled |
| Operation | The operation behind it: `install`, `upgrade`, `downgrade`, `restart` or `uninstall` |
| Version | The version the installation runs once the change is done; after a failed upgrade or downgrade, the installed version that keeps serving (the message names the target) |
| Message | What happened, such as `started` or the failure message |
| Cause | The detail behind a failure, or how Pragmatiks stopped a worker it replaced (such as `stopped: did not answer a cancel`) |

The history is kept for 30 days, also after the provider is uninstalled. `-o json` and `-o yaml` print the entries as records.

## Upgrade and Downgrade

Move an installed provider to another version:

```bash
pragma providers upgrade pragmatiks/postgres
pragma providers upgrade pragmatiks/postgres --version 2.0.0
pragma providers downgrade pragmatiks/postgres --version 1.2.0
```

`upgrade` without `--version` targets the latest version. `downgrade` requires `--version`. Like `install`, both print the target version and point to `pragma providers history`. The installed version keeps serving until the new one runs.

Install, upgrade, downgrade and uninstall are also refused when they would break an installed provider that embeds another, or drop a resource type your resources use; the message says what to run instead. See [Compatibility Checks](#compatibility-checks).

An upgrade or downgrade is refused while another operation on the provider is running. A failed installation cannot be downgraded; install the version you want instead:

```bash
pragma providers install pragmatiks/postgres --version 1.2.0
```

## Compatibility Checks

Pragmatiks refuses an install, upgrade, downgrade or uninstall that would break something you run. The refusal says what to do, and nothing changes until you do it.

### Providers That Embed Other Providers

A provider can embed other providers. It can be installed only when every provider it embeds, directly or through another provider, is installed. The refusal names each missing provider with the command and version to install:

```text
acme/outer embeds acme/inner and acme/middle, which are not installed. Run: pragma providers install acme/inner --version 1.0.0; pragma providers install acme/middle --version 1.2.0
```

### Changes That Would Break an Embedding Provider

An install, upgrade or downgrade is refused when it would break an installed provider that embeds another. This happens in two cases.

An upgrade of the embedded provider drops or changes outputs, or configuration fields, that an embedding provider reads:

```text
Upgrading acme/p to 2.0.0 drops or changes outputs acme/c reads: embedded.imported_packages. Upgrade acme/c to a version built against acme/p 2.0.0, or keep the installed version.
```

An embedding provider expects outputs the installed provider does not provide:

```text
acme/c 1.1.0 reads outputs installed acme/p 1.0.0 does not provide: embedded.zone. Upgrade acme/p first, or upgrade acme/c to a version built against acme/p 1.0.0. Run: pragma providers upgrade acme/p --version 1.1.0
```

Adding outputs never breaks an embedding provider.

### Resource Types That Would Disappear

A version change is refused when the new version drops a resource type that your resources still use. Resources in draft do not count. The refusal names the resources:

```text
Upgrading acme/p to 4.0.0 drops resource type embedded, which 2 resources use: acme/p/embedded/a, acme/p/embedded/b. Delete them first, or keep the installed version.
```

### Applying Resources

Applying a resource is refused while its provider is being uninstalled:

```text
provider acme/p is being uninstalled. Wait for the uninstall to finish, then install it again before applying resources of its types.
```

It is also refused when the installed version does not define the resource type:

```text
pragmatiks/gcp 8.0.0 does not define resource type cloudsql/user. Upgrade or downgrade pragmatiks/gcp to a version that does, or delete the resource.
```

Resources that a provider creates for you belong to the provider that defines their type, so that provider must be installed too. See [Resource Lifecycle](/building-providers/lifecycle).

## Installation lifecycle

An install, upgrade or downgrade goes through these states:

| State | Meaning |
|-------|---------|
| `Queued` | The operation is accepted and waits to start |
| `Starting` | Pragmatiks is preparing and starting the provider at the target version |
| `Running` | The provider serves its resources |
| `Failed` | The operation did not finish; the message says why |
| `Uninstalling` | `pragma providers uninstall` is removing the provider |

A running provider that restarts shows `Starting` until it serves again, and its history records when it stopped, why, and when it started again.

When an installation fails, `pragma providers list --installed` and `pragma providers history` show the reason, naming the step it stopped in when it ran out of time, for example:

```text
Installing acme/pipeline 2.0.0 did not finish in time while installing the provider's dependencies. Install it again.
```

Recover by installing it again, at the version you want:

```bash
pragma providers install acme/pipeline --version 2.0.0
```

The web console shows the same state on the provider page, an **Install again** button for a failed installation, and the installation history.

## Uninstall

Uninstall a provider from your organization:

```bash
pragma providers uninstall pragmatiks/qdrant
```

Uninstall a provider and delete all its resources:

```bash
pragma providers uninstall pragmatiks/postgres --cascade
```

<Warning>
The `--cascade` flag deletes all resources managed by the provider. This action cannot be undone.
</Warning>

## Delete

Delete a provider and all its versions:

```bash
pragma providers delete myorg/my-provider
```

Only admins of the organization that owns the provider can delete it. Delete is refused while the provider is installed in any organization: uninstall it everywhere first. It is also refused while one of its versions is `promoting`, until that version is `published` or `failed`. `--yes` skips the confirmation prompt.
