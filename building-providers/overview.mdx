Providers let you extend Pragmatiks to manage any tool, service, or infrastructure. A provider packages the logic to observe, create, update, and delete resources of specific types.

## Why Build a Provider?

Build a provider when you want to:

- **Manage internal tools** - Bring your proprietary systems into the Pragma ecosystem
- **Support new services** - Add resources for cloud services, databases, or APIs not yet covered
- **Standardize operations** - Encode your team's best practices into reusable resource types
- **Enable reactive pipelines** - Let your resources participate in dependency-driven workflows

Once deployed, your provider's resources work like any other Pragma resource: users apply configurations, the platform handles lifecycle events, and outputs propagate through dependency chains.

## Provider Architecture

A provider consists of three main components:

### Provider

A namespace that groups related resources. Think of it like a FastAPI router that collects related endpoints.

```python
from pragma_sdk import Provider

gcp = Provider()
```

### Resource

The core abstraction. Each resource type:

- Has a **Config** schema defining what users configure
- Has an **Outputs** schema defining what it exposes to other resources
- Implements **lifecycle methods** to observe its external object and handle create, update, and delete events

```python
from pragma_sdk import Config, Field, ImmutableField, Outputs, Resource


class DatabaseConfig(Config):
    """Configuration for a database.

    Attributes:
        name: Database name. Locates the database, so it cannot change.
        size_gb: Storage size in gigabytes.
    """

    name: ImmutableField[str]
    size_gb: Field[int] = 10


class DatabaseOutputs(Outputs):
    """Outputs of a database.

    Attributes:
        connection_url: Connection string for clients.
    """

    connection_url: str


@gcp.resource("database")
class Database(Resource[DatabaseConfig, DatabaseOutputs]):
    """Database located by its name."""

    async def on_create(self) -> DatabaseOutputs:
        """Create the database and return its outputs."""
        ...

    async def on_observe(self) -> DatabaseOutputs | None:
        """Find the database by name; return its outputs, or None when it does not exist."""
        ...

    async def on_update(self, previous_config: DatabaseConfig | None) -> DatabaseOutputs:
        """Converge the database to the current configuration."""
        ...

    async def on_delete(self) -> None:
        """Delete the database; succeed when it is already gone."""
        ...
```

### Config and Outputs

Both extend Pydantic `BaseModel` with `extra="forbid"` to catch typos and invalid fields:

- **Config**: User-provided settings. Define required fields, defaults, and validation.
- **Outputs**: Values your resource exposes. Other resources can reference these fields.

## Lifecycle Methods

Every resource implements four async methods:

| Method | Called When | Returns |
|--------|-------------|---------|
| `on_create` | Resource is first provisioned | `Outputs` |
| `on_observe` | The platform needs the object's current state | `Outputs`, or `None` when the object does not exist |
| `on_update` | Configuration changes, or a create finds the object already present (`previous_config=None`) | `Outputs` |
| `on_delete` | Resource is removed | `None` |

`on_observe` locates the object from the resource's identity and config alone, never from stored outputs. It is mandatory unless the resource declares `computed = True` because it owns no external object; publishing a provider that omits it fails naming the resource type.

These methods must be **idempotent**. The platform may retry events if delivery fails, so calling a lifecycle method twice with the same input should produce the same result. A create that finds the object already made by an earlier attempt reuses it:

```python
async def on_create(self) -> SecretOutputs:
    try:
        secret = await client.create_secret(...)
    except AlreadyExists:
        secret = await client.get_secret(...)

    return SecretOutputs(resource_name=secret.name)
```

## Prerequisites

Before building a provider, you need:

- **Python 3.13+** - Providers use modern Python features
- **uv** - Fast Python package manager (install via `curl -LsSf https://astral.sh/uv/install.sh | sh`)
- **pragma-sdk** - The SDK provides `Provider`, `Resource`, `Config`, and `Outputs` classes
- **Pragmatiks CLI** - For initializing projects and deploying (`pragma providers init`)

## Project Structure

Initialize a provider project:

```bash
pragma providers init mycompany
cd mycompany-provider
```

This creates:

```
mycompany-provider/
├── pyproject.toml
├── README.md
└── src/mycompany_provider/
    ├── __init__.py
    └── resources/
        ├── __init__.py
        └── example.py
```

| Path | Holds |
|------|-------|
| `pyproject.toml` | Package metadata and the `[tool.pragma]` table `publish` reads |
| `src/mycompany_provider/__init__.py` | The `Provider` instance and resource registrations |
| `src/mycompany_provider/resources/` | Your resource implementations |

## Deploying

Once your provider is ready, publish a version and install it in your organization:

```bash
pragma providers publish
pragma providers install <org>/mycompany
```

After the platform deploys it, users can create resources of your types:

```yaml
provider: mycompany
resource: database
name: analytics
config:
  name: analytics
  size_gb: 100
```
