The `pragmatiks/pragma` provider, installed in every organization, provides a `pragma/file` resource for uploading and managing files. Files are stored in platform storage, belong to a project, and expose outputs that other resources can reference.

## Prerequisites

- pragma CLI installed and authenticated (`pragma auth login`)

## Using the CLI

### Upload with @path syntax

The simplest way to upload a file is using the `@path` syntax in your YAML config:

```yaml
provider: pragmatiks/pragma
resource: file
name: training-data
config:
  content: "@./data/training-set.jsonl"
  content_type: "application/jsonl"
```

```bash
pragma resources apply training-data.yaml
```

The CLI:
1. Reads the file from the local path (relative to the YAML file's directory)
2. Uploads the file straight to storage, into the project the command applies to, and waits until it is stored
3. Applies the `pragma/file` resource with `content` set to the file's reference, `pragma://files/training-data`

The CLI uploads every `@path` file before it applies anything, so a resource that reads the file never runs before its bytes exist.

### Upload limits

- A file can be up to about 5 GiB.
- The whole file must reach storage before the upload address expires: one hour plus about 34 minutes per GiB (assuming 4 Mbit/s). Larger files take a little while to be stored after the upload ends, and the CLI waits for that.
- An interrupted upload starts again from the beginning.
- Uploading the same file again does not send it again.

### File names

A file name cannot be empty, `.` or `..`, or longer than 255 bytes. It cannot contain a path separator or a control character. A `pragma://files/<name>` reference must name a valid file, and one resource config can hold at most 32 distinct references. Otherwise the apply is refused with `422`.

### Project scope

Files belong to a project, not to your organization. The same file name in two projects is two separate files. A `pragma://files/<name>` reference resolves to the file in the referencing resource's project.

### File Outputs

After the file resource reaches `ready` state, it exposes these outputs:

| Output | Description |
|--------|-------------|
| `url` | The file's `pragma://files/<name>` reference, which other resources' configs take |
| `size` | File size in bytes |
| `content_type` | MIME type |
| `checksum` | MD5 of the content, as hex, verified by storage when the file is uploaded |
| `uploaded_at` | Upload timestamp |

View the outputs:

```bash
pragma resources describe pragmatiks/pragma/file/training-data
```

The outputs are read when the resource is first applied. Applying the resource again does not refresh them yet, so they can lag behind new content uploaded under the same name.

### Deactivating and deleting a file resource

A `pragma/file` resource reads only its own file, the one uploaded under the resource's name, so its `content` is always `pragma://files/<resource name>`.

- Deactivating the resource keeps the uploaded file. Applying it again finds the stored file; when its `content` is `"@<path>"`, `pragma resources apply` uploads the file again.
- Deleting the resource deletes the uploaded file shortly after. Resources that reference the file resource fail, because their dependency is deleted. Until the file is deleted, applying the resource again is refused with `409` (`file_delete_in_progress`); try again shortly and it uploads afresh.
- Deleting the resource while a new upload of its file is still being stored is refused with `409` (`file_upload_in_progress`). Delete it again once the upload is stored.

## Downloading a file

Downloading is available through the API only: neither the SDK nor the CLI has a download command.

The download route, `GET /projects/{project_id}/files/{name}/download`, is the `public_url` that the SDK's `upload_file` returns; the resource's outputs carry no `public_url`, so `upload_file` is its only source. It needs Pragmatiks credentials. It answers with a redirect (`307`) to a short-lived download address, so your client must follow redirects. Your credentials go to Pragmatiks only; the download address carries its own signature and needs none.

```bash
curl -L -H "Authorization: Bearer $(pragma auth token)" "<public_url>" -o training-data.jsonl
```

In Python with httpx, pass `follow_redirects=True`. Without credentials the request is refused with `401`.

To get a short-lived download address that needs no credentials, call `GET /projects/{project_id}/files/{name}/url`. The response holds the address and its expiry. Anyone who has the address can download the file until it expires, so treat it like a secret.

When an address cannot be prepared, these requests answer `503` with `file_url_unavailable` and a `Retry-After` header. See [Errors](/api-reference/errors#retry-later-503).

<Note>
Despite its name, `public_url` is not open to the public. Do not pass it to a service that sends no credentials. Use a `pragma://files/<name>` reference instead (see [Referencing Files from Other Resources](#referencing-files-from-other-resources)).
</Note>

## Using the SDK

### Upload programmatically

Upload through the project handle so the file lands in that project.

```python
from pathlib import Path

from pragma_sdk import PragmaClient

with PragmaClient() as client:
    project = client.project("my-project")
    file = project.upload_file(
        name="training-data",
        source=Path("training-data.jsonl"),
        content_type="application/jsonl",
    )

    print(f"Uploaded: {file.public_url}")

    # Create the file resource to track it
    project.apply_resource({
        "provider": "pragma",
        "resource": "file",
        "name": "training-data",
        "lifecycle_state": "pending",
        "config": {"content": "pragma://files/training-data"},
    })
```

The upload goes straight to storage and returns once the file is stored. An interrupted upload starts again from the beginning.

## Referencing Files from Other Resources

Reference a file through its file resource's `url` output, which holds `pragma://files/<name>`. The reference makes the file resource a dependency, so deleting the file resource shows on the resources that read it. For example, to use an uploaded document as a knowledge source for an AI agent:

```yaml
# Upload the document
provider: pragmatiks/pragma
resource: file
name: product-docs
config:
  content: "@./docs/product-manual.pdf"
  content_type: "application/pdf"
---
# Knowledge base references the file resource's url output
provider: pragmatiks/agno
resource: knowledge
name: product-knowledge
config:
  source_url:
    provider: pragmatiks/pragma
    resource: file
    name: product-docs
    field: outputs.url
```

A config can also hold `pragma://files/<name>` directly, but then nothing links it to the file resource: deleting the file resource leaves it unchanged until its next operation, which fails because the file is gone. A `pragma://files/<name>` reference resolves to the file in the referencing resource's project, and Pragmatiks supplies a short-lived download address when the resource runs. Do not use the `public_url` from `upload_file` here: it needs credentials, which a knowledge source does not send.

## Supported Content Types

Any MIME type is supported. Common examples:

| Content Type | Use Case |
|-------------|----------|
| `application/pdf` | Documents, manuals |
| `application/json` | Configuration files, datasets |
| `application/jsonl` | Training data, log files |
| `text/plain` | Text documents, CSV files |
| `text/csv` | Tabular data |
| `image/png`, `image/jpeg` | Images |
