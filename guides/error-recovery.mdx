When a resource fails, pragma captures the failure details and gives you the tools to diagnose, fix, and retry. This guide walks through identifying failures, understanding their causes, and getting your infrastructure back to a healthy state.

## Identifying Failed Resources

Resources in a failed state appear with `[FAILED]` when listed:

```bash
pragma resources list
```

Output shows lifecycle states for all resources:

```text
Provider         Resource  Name       State    Updated
pragmatiks/gcp   storage   data-lake  ready    2026-03-02 09:12:44
pragmatiks/agno  agent     assistant  failed   2026-03-02 09:14:03
pragmatiks/agno  team      my-team    waiting  2026-03-02 09:14:05
```

To see details about a specific failed resource:

```bash
pragma resources describe pragmatiks/agno/agent/assistant
```

## Automatic Recovery

### Operation Deadline

Every operation has 20 minutes by default to finish, counted from the moment the provider starts running it. A resource type can declare a longer limit, up to one hour. A long operation stays alive for as long as its provider keeps responding; one that stops responding fails sooner. When the deadline passes, Pragmatiks cancels the operation and the resource moves to `failed` with this message:

```
Resource <id> did not finish within <seconds> seconds. Apply again to retry it, or deactivate the resource to discard it.
```

An operation waiting for a provider that is not running has no deadline. It starts once the provider runs, and its deadline counts from then.

To retry, apply the resource again. To discard it, deactivate it.

If you apply a changed configuration while a resource is `processing`, Pragmatiks queues it and applies it as soon as the running operation ends. The resource shows as `processing (apply queued)` until then.

### Idempotent Apply

Re-applying a resource with the same configuration is safe. If the resource is already `ready` with identical config, Pragmatiks returns the existing resource without re-processing. This makes it safe to re-run `pragma resources apply` in scripts without side effects.

## Common Failure Scenarios

### Configuration Errors

The most common cause of failure is invalid configuration:

- **Missing required fields** — A required config value is missing
- **Invalid values** — A value doesn't match the expected format or constraints
- **Permission errors** — The provider doesn't have access to create or modify the resource

**Recovery**: Fix the configuration in your YAML file and re-apply:

```bash
pragma resources apply fixed-resource.yaml
```

### Dependency Failures

A resource can fail or wait if its dependencies aren't satisfied:

- **Missing dependency** — A referenced resource doesn't exist, or was deleted: the apply is refused. A resource whose dependency is deleted later moves to `failed`.
- **Dependency not ready** — A dependency exists but is not `ready` yet, or is in `failed` state: the resource waits in `waiting`, and `describe` lists the dependency under `Blocked by:`.
- **Invalid field reference** — A FieldReference points to a field that doesn't exist in the dependency's outputs: the resource moves to `failed`.

**Recovery**: Ensure all dependencies are in `ready` state:

```bash
# Check dependency status
pragma resources describe pragmatiks/agno/anthropic-model/claude

# If dependency is failed, fix and re-apply
pragma resources apply model.yaml
```

Once the dependency reaches `ready`, waiting dependents are processed automatically.

### Provider Errors

Sometimes the underlying provider rejects the operation:

- **Quota exceeded** — You've hit a service limit
- **Resource conflicts** — A resource with that name already exists outside pragma
- **Service unavailable** — Temporary provider outage

**Recovery**: Address the provider-specific issue, then retry the resource.

## Dependency Failure Cascades

When a resource fails, it affects downstream resources:

1. **Failed resources stay failed** — They don't retry automatically; apply them again after fixing the cause
2. **Waiting dependents keep waiting** — Resources waiting for a failed dependency remain in `waiting`, with health `blocked`, until the dependency becomes `ready`
3. **Ready dependents are degraded** — A ready dependent stays `ready` with its current configuration, and its health is `degraded`; `degraded_by` names the failed dependency
4. **Dependents recover automatically** — When you fix the dependency and it reaches `ready`, waiting dependents are processed, and degraded dependents are resolved again and updated if their configuration changed

Consider this dependency chain:

```text
secret (READY) → model (FAILED) → agent (WAITING)
```

The `agent` resource can't proceed because `model` is failed; `pragma resources describe` shows it as `blocked` by `model`. To recover:

1. Fix the `model` configuration
2. Re-apply to retry
3. Once `model` reaches `ready`, `agent` automatically proceeds

## Recovery Workflow

When you encounter failures, follow this workflow:

<Steps>
  <Step title="Identify failures">
    ```bash
    pragma resources list
    ```
  </Step>
  <Step title="Investigate root cause">
    ```bash
    pragma resources describe <organization>/<provider>/<resource>/<name>
    ```
  </Step>
  <Step title="Fix the issue">
    Update your YAML configuration, fix permissions, or address provider limits.
  </Step>
  <Step title="Retry">
    ```bash
    pragma resources apply fixed-resource.yaml
    ```
  </Step>
  <Step title="Verify">
    ```bash
    pragma resources describe <organization>/<provider>/<resource>/<name>
    ```
    Confirm the resource reaches `ready` state.
  </Step>
</Steps>

## Preventing Failures

Reduce failures by:

- **Using draft mode** — Apply with `--draft` first to validate configuration, then re-apply without `--draft` to deploy
- **Checking dependencies** — Use `pragma resources describe` to verify dependencies are `ready`
- **Applying in bulk** — Apply all resources in a single YAML file; Pragmatiks resolves the dependency order automatically
